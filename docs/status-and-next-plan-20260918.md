## 1. 结论

**目前处于“阶段 0 已交付，阶段 1 尚未完整验收，阶段 2 API 契约草案已形成并通过结构及示例验证、服务实现未开始”的位置。** 已有可嵌入 Java 应用的执行内核与能力包，不能称为已建成的 Agent 中台。

下一步建议：**先处理 CI 基线问题，阶段 1 收尾与阶段 2 事务底座并行，再交付最小集中执行服务；服务验收后进入控制台与资源发布。** 不需要重新实现 AgentLoop，也不宜先扩建 Workflow 画布、向量库或模型后台。

本计划承接《评估 AgentLoop harness 重构》中的已选方案：独立 Harness 仓库，保留嵌入式 SDK，在其上逐步建设内部多业务 Agent 中台。沿用原来的六阶段编号，不把本次细分工作包当作新的全套路线。当前假设仍是单组织内部平台，不扩展为对外多租户 SaaS。

## 3. 为什么服务化要先补底座

代码核对确认以下差距，不是单纯缺 Controller：

| 差距 | 当前代码依据 | 下一步必须形成的能力 |
|---|---|---|
| 控制入口没有调用方 revision | `Harness.java` 的 `pause/cancel/resume/decide/reconcileTool` 内部读取当前 revision | 调用方 `expectedRevision` 原子校验；过期 ETag 不能改变状态 |
| 平台事务无法直接组合 | `JdbcRunStore.transaction` 内部自行获取连接并提交；现有原子边界是 Run + event | 归属、额度、Run、事件、命令幂等响应同事务提交；不能简单依赖外层 Spring 注解 |
| 身份仅为 SDK 契约 | `Actor` 只有 subject/project/permissions；默认权限策略不是外部身份系统 | 服务端可信身份、project/application/effectiveSubject 归属、动态撤权、审批分配 |
| 没有后台运行宿主 | `tick/tickReady` 需宿主调用；`ready` 仅选 QUEUED/RUNNING | 持久调度、等待到期扫描、停机/租约回收、共享基本额度 |
| 对账入口信任宿主回执 | `reconcileTool` 接受已核验结果，不负责核验远端证据 | 独立证据来源与精确 invocation/参数/契约绑定；HTTP 不接受随意声称成功 |
| 公开查询与配置层缺失 | store 没有面向用户的 Run 列表；完整状态含内部数据 | 授权索引、DTO 投影、签名游标、不可变 release manifest、Secret Provider |

具体契约仍以 [阶段 2 API 设计](phase2-api-design.md) 为基础；实现过程中记录必要调整，在内部开放前冻结 v1。

## 4. 下一步工作包与验收顺序

### P0：先固定可复现的工程基线

工作：针对已经定位的取消/revision 竞争，增加确定性同步点复现交错，明确 core 与 worker 对取消状态收敛的责任；据此修复实现或不准确的测试同步假设，不能单纯加 sleep、放宽断言或屏蔽测试。保留本轮验证记录，将历史说明与当前状态分开；确定后续开发分支和可追溯构建标识。

完成标准：对应候选提交的 Windows、Linux、API 契约检查均通过；报告绑定提交和制品校验和。不能把本机成功或重复点击重跑当作失败根因已经解决，也不因 CI 报错便扩大改写整个框架。

### P1：阶段 1 收尾，独立工作线

1. **可信业务身份桥。** 在 OpsAgent 测试环境实现已认证平台主体到业务用户的绑定、短期运行身份签发与逐次撤权检查，先接只读知识检索。
2. **持久请求归属。** 用唯一约束和输入摘要保存新请求选择的执行器；重试沿用原归属；切换开关只作用于新请求；重启后归属不丢，失败和 UNKNOWN 不自动交给另一执行器。
3. **真实受控写验收。** 选择独立测试资源和可查询回执的真实工具，验证批准后写入、写后断连、UNKNOWN 保留及独立证据对账。现有本地合成写不能代替这项。
4. **业务质量基线。** 为检索/回答建立带预期引用和权限范围的小型标注集，分别报告检索命中、引用正确性、权限泄露和答案质量；首次运行确定基线，再冻结后续发布阈值。

完成标准：测试部署的身份与知识权限成立；持久归属和新请求回退开关演练通过；实际受控写及对账有报告；两个场景使用同一核心并有可复现的差异清单。

这条线可与下面 P2A 并行。真实部署或写工具暂未就绪时，继续合成场景服务开发，同时保持阶段 1 未完成；受影响的业务接入或写能力不进入开放验收，不能静默删除原验收项。

### P2A：阶段 2 第一批——命令与事务底座

工作顺序：

1. 为核心控制/审批/对账设计一致的命令入口，接受调用方 revision，并保留现有状态机规则；评估 SDK 源码与状态兼容影响。
2. 为 JDBC 提供明确的事务组合边界，让平台归属、额度预留、Run、事件、幂等响应共用事务。数据库事务内不调用模型或工具。
3. 增加命令幂等账本、项目/应用/主体归属索引和迁移脚本，定义同键不同体、保留期及旧状态处理。
4. 分离人工输入和审批审计理由，保留精确审批摘要和 UNKNOWN 约束。

完成标准：同键并发只接受一次；接受后丢失响应仍可恢复首次结果；旧 revision 无任何业务副作用；模拟任一写入失败时，Run/事件/归属/配额/幂等响应整体回滚。覆盖 worker 与控制命令竞争。

**这是建议首先启动的功能开发批次。** 它不依赖控制台或真实业务环境，可在当前仓库直接推进，并解决后续所有平台入口共用的可靠性问题。

### P2B：阶段 2 第二批——最小集中执行闭环

建议采用 Java 17 + Spring Boot 的模块化服务外壳，核心仍为普通 Java。先按 SQL 调度，保持 API 与 worker 的职责和启停边界；开发阶段允许同一部署单元，不预先引入消息队列、微服务拆分或 Kubernetes。

交付：

- 可信服务/用户身份、项目/应用/主体归属、实时授权；开发测试身份与实际试点身份明确区分。
- 部署时加载的不可变 release manifest、输入校验和受控输出；凭据引用及目标 allowlist。
- 创建 Run、Run 列表/查询、游标事件 API；HTTP 返回 202 后由后台 worker 推进。
- 最小共享排队上限、额度预留和后端并发限制；凭据不进入 RunState、日志或 DTO。
- 两类合成场景通过 HTTP 客户端运行，使用 MySQL 持久账本；代码调用者无需自己循环 `tick`。

完成标准：进程重启不丢已接受 Run；重复请求不重复接受；两项目 × 两应用 × 两主体的读取、列表、事件和幂等重放隔离测试通过；客户端不能自报权限或替换模型/MCP 目标；额度拒绝不留下部分 Run。

### P2C：阶段 2 第三批——控制治理与试点验收

补齐 11 操作的实际 HTTP 实现：暂停、取消、恢复、审批读取/决定、UNKNOWN 查询和证据对账；补齐等待到期、优雅停机、健康检查、日志/trace、部署与备份恢复操作说明。

验收使用真实进程终止与重启、两 worker 争抢、MySQL 重启及受控故障注入。必须保留预算/期限/审批基线，旧 worker 的过期 fence 不能提交；未知写不能被取消、到期或重启隐藏，也不能自动重发。撤权后，列表、事件、审批、证据和幂等重放均受当前授权限制。

完成标准：11 个操作有 HTTP 行为测试而非仅 schema 检查；身份/配额/幂等/故障恢复门槛通过；两类场景可由受控客户端调用；部署、备份与恢复可复现；P1 与对应接入范围相关的验收已闭合。模型调用 UNKNOWN 仍按 v1 已声明的操作边界处理，不伪装成工具证据对账。

达到这里可以称为**可内部试用的集中执行服务**，还不是完整中台 MVP。

### P3：阶段 3——配置发布与管理入口

执行服务稳定后建设 Agent、模型、Prompt、工具、RAG、Workflow 的资源目录及草稿/校验/发布/停用流程；再建 Run 列表与详情、待审批和对账页面，并提供薄客户端 SDK。

完成标准：至少两个实际受控调用方通过同一平台配置、调用、审批和追踪；新发布不改变既有 Run 的快照；权限撤销仍约束后续执行；调用方不再各自托管执行账本和审批引擎。**此时达成中台 MVP。**

后续阶段 4–6 保留原路线：公共能力产品化 → 容量/成本/SLO/恢复治理 → 分批业务迁移与旧执行职责退出。不要在下一批同时承诺全部交付。
