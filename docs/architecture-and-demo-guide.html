从业务闭环，理解
OpsAgent 与 Agent 应用平台。

OpsAgent 负责运维业务与知识；中台提供可复用的应用构建、发布和受控执行；独立客服验证第二种业务接入。两者已在明确的问答链路完成对接，仍保留原有流式会话与运维 Agent。

01 / ARCHITECTURE

当前架构：一个公网入口，三个工作界面。

部署在一台 12 GB 规格 VPS 的 Docker Compose 中。最近交付快照为 28 个运行服务。图中按职责分组，不把每个模块都画成一条独立链路；这是单机部署，不是高可用集群。

Ops 业务服务中台与独立业务应用共享基础设施 / 外部模型

实线表示主要调用或数据依赖；虚线表示中台对 Ops 身份与知识授权的回查。组件被合并展示；私网 TLS 代理、采集器及部分单独容器没有逐个绘制。

业务层

OpsAgent

解决“发生了什么、如何处理、依据是什么”。保留工单、知识、来源权限、运维处置及业务界面。

共享能力层

Agent 应用平台

解决“谁能调用哪个版本、运行到哪一步、谁批准、花了多少、未知结果怎么办”。提供应用生命周期和执行账本。

复用验证

独立客服

使用另一应用身份与界面调用同一中台，验证生成后人工审核、用户隔离与原答案交付，不复刻 Ops 业务系统。

02 / INTEGRATION BOUNDARY

“已对接”成立，但范围需要说准确。

已验证的是后端受控知识问答接入及客服接入。当前 Ops 页面以流式体验为主，不能把任意一次页面聊天都当成中台 Run。

03 / COMPLETE USER JOURNEYS

四条可讲清楚的闭环路线。

建议先走 D 和 B，让观众看到结果，再根据关注点展开 A 或 C。以下为操作路线；本指南没有再次发起模型请求、故障演练或修改生产发布。

A

知识 → 发布 → 有据回答 → 回到原文

面向业务 / RAG 能力 · 管理员或知识维护者 + 有阅读权限的用户 · 约 3–5 分钟

入口：知识与经验 → 知识审核 → 智能问答

  1. 准备文档选择已有维护手册，展示正文、版本和切片。若现场新增，只上传自己有权演示的资料。
  2. 完成发布新资料先上传、解析，提交审核后由有权限的角色发布；检查索引管理状态，不把“已上传”当“可检索”。
  3. 基于事实提问在智能问答提出手册中可核对的问题，例如“故障恢复后如何核对业务已恢复？”
  4. 核验引用展开参考上下文，跳回来源，核对版本、片段和答案。展示历史记录可读，必要时对比没有证据的问题。

闭环结果一份经过审核的知识成为可追溯回答，答案能回到真实来源；现场主问答页展示的是 Ops 流式链路。

预条件与边界需已发布且有权读取的知识、索引可用、模型已配置。当前停用 reranker；HYBRID_RRF 是已验召回方式，不保证每条查询都有向量命中。

B

真实故障 → 诊断 → 审批 → 恢复 → 事件关闭

面向运维 / Agent 工程 · 获授权运维或管理员，访客仅本人隔离场景 · 约 4–8 分钟，模型与监控需等待

入口：自动化中心 · 我的演练 → “运行与审批” → 关联 事件处置

  1. 确认健康基线选择 Nacos Redis 配置漂移、Sentinel 限流或 RabbitMQ 消费暂停。推荐每次只展示一类；目标健康且按钮可用时才发起。
  2. 看诊断依据观察实际业务异常、告警、工单和 Agent 运行。解释它读取了哪些配置 / 指标，如何形成处置计划。
  3. 批准具体动作打开待审批，核对同一事件、目标、配置修订及具体参数，然后批准。展示“模型建议”与“执行权限”分离。
  4. 核对真正恢复看恢复工具回执、业务探针 200、连续成功、同一告警解决、工单 RESOLVED 和 Run COMPLETED，而不只看绿色标签。

闭环结果从业务故障到可证明的恢复。稳定的回看素材：工单 2099（Nacos）、2101（Sentinel）、2103（Rabbit）；它们属于 Ops 运维 Agent。

预条件与边界实时演练会改变隔离目标，现场不并发启动。不成功时如实展示 NEEDS_ATTENTION 与人工接管；人工或 TTL 恢复不能称为 Agent 成功。不要现场测试陌生生产目标。

C

应用草稿 → 体验 → 评测 → 发布 → 使用反馈

面向平台 / 研发 · 有 Studio 编辑、评测、发布和运行权限的项目用户 · 约 4–6 分钟

入口：中台 · 应用 → 某应用 Studio → 任务工作台

  1. 定义可交付助手从模板创建独立演示应用，选已授权模型，写任务目标；按需要绑定知识和工具。保存草稿再体验。
  2. 先体验与评测在“构建与体验”试问，把有代表性的输入加入固定样本；在“评测”比较候选与基线，查看结果和规则。
  3. 固定版本发布进入“发布与接入”，核对模型、能力、运行策略和评测结果，审阅后确认。不要为演示覆盖正在被业务使用的默认版本。
  4. 以正式版本使用打开已发布助手，创建任务，查看结果和处理轨迹，再到“运行与反馈”回看。草稿后续变化不会改写已有任务快照。

闭环结果从想法到有版本、有评测、有运行反馈的助手，解释中台为何不是“又一个聊天界面”。

预条件与边界真实体验与评测会调用模型。含人审的样本也需要指定审核员处理；规则通过不等于全面模型质量证明。“应用接入”审批后仍需真实身份配置和生效核验。

D

客服咨询 → 生成待审答案 → 审核 → 原答案交付

面向中台复用 / 人在回路 · 分别获授权的客服专员和审核员 · 约 3–5 分钟

入口：独立客服工作台；查看中台配置时，先打开 中台应用列表，在顶部切换到已获授权的 support-prod 项目，再打开“客服助手（尚未配置业务知识）”（应用标识 support-empty-knowledge）。

  1. 专员提交咨询选择已正式发布的客服助手，提一个符合当前知识范围的问题，保存本次运行编号。
  2. 展示“待审核”解释答案已经生成，但还没有作为最终交付完成。把同一 Run 编号交给审核员，不重新提交一个问题。
  3. 审核员核对退出后以审核员身份登录，输入 Run 编号，检查完整待审内容和依据，填写说明，再“确认并继续”或拒绝。
  4. 专员读取交付重新以专员登录，打开原运行，核对 COMPLETED 与原答案。批准不会触发第二次生成，也不会把审核意见当成答案。

闭环结果第二业务应用复用中台 Run、发布与审批。已有真实样例 ac2262e3-bdaa-404b-bbf6-99285ed7f9a6 为一次模型调用，审核前后答案摘要一致。

预条件与边界当前公网客服没有真实业务知识，因此应明确转人工，不编造政策；未接真实订单、退款或客户消息发送。浏览器角色下拉不授予权限，须使用已获授权身份。

04 / THE 12-MINUTE DEMO

面试演示：一个业务结果，三个工程问题。

主线建议：先让对方看懂系统解决什么，再展示“如何安全执行、如何追溯依据、如何被第二个应用复用”。不用逐个介绍 28 个容器。

“我把 OpsAgent 的业务能力和可复用的 Agent 运行平台分开。业务系统负责证据和权限，中台负责版本、执行、审批与账本。先用受控问答打通，再用独立客服验证它能服务另一种业务。”
0:00–1:30

给出场景与架构边界

展示运行总览和本页架构。指出三个入口共用身份源但各自会话；说明单 VPS 部署及原运维 Agent 尚未迁移。

讲法：“不是把所有功能搬进中台，而是明确谁管业务、谁管可复用的运行协议。”

1:30–5:00

展示一个故障处置闭环

走路线 B：时间紧先回看已完成 Rabbit 工单 2103 的故障、审批、回执、恢复证据；有充足时间才发起新隔离演练。不要把生成模型的等待伪装成已完成。

讲法：“审批绑定具体动作与参数，绿色结果来自业务恢复证据；模型答得像，不代表已经修好。”

5:00–7:00

把答案与证据对应起来

走路线 A 的后半段：打开既有维护手册，问一个有答案的问题，展开引用。再切中台已有 Ops 问答 Run，看固定 release、事件和调用账本，清楚标注两种执行链路。

讲法：“来源权限不只在检索时校验，读取历史平台答案时也要重新确认，避免撤权后仍泄露答案。”

7:00–10:30

用独立客服证明中台复用

走路线 D：专员提交 → 审核员核对 → 原答案交付；旁边展示 Studio 的正式发布配置和对应 Run。只读介绍现有发布即可，不必现场改生产策略。

讲法：“第二个应用没有复制运行引擎，仍复用版本、隔离、人审和执行账本；它自己的业务知识目前还待接入。”

10:30–12:00

用工程取舍结束

展示一次 UNKNOWN / NEEDS_ATTENTION 的保留记录，说明不盲重放、不把失败隐藏。概括租约与版本竞争控制、幂等键和输出 ACL；明确七天观察与异机恢复未验。

讲法：“我能保证账本、审批和请求归属的规则，但不承诺任意第三方调用 exactly-once；未知结果需要核验。”

五分钟压缩版：架构 45 秒 → 已完成故障回看 90 秒 → 客服人审闭环 2 分钟 → 边界与取舍 45 秒。后端岗位重点讲状态机、事务与权限；AI 应用岗位重点讲证据、评测和人审；平台岗位重点讲发布、隔离和第二业务复用。
为什么不把 OpsAgent 全部迁进中台？

工单、告警、业务恢复、文档权限属于业务域。先迁明确、可验证的受控问答执行链路，保留 SSE 和已有运维工作流，可降低一次性迁移风险。后续迁移应独立设计行为兼容、账本与回退策略。

为什么不只调用一次模型 API？

真实应用还要处理固定发布、创建幂等、审批、暂停取消、权限撤销、费用与未知结果。单次模型调用只覆盖其中一步，中台把这些可复用运行规则从各业务中抽出来。

写操作超时后会怎样？

远端可能已执行，不能以“超时”推断未执行。保留 UNKNOWN、调用和预算账本，不跨执行器自动重放；对可核验工具，由授权流程核对远端回执再决定后续。

12 GB 单机能证明什么？

已证明当前选定服务和业务短时验收可运行。最终交付采样约有 4.6 GiB MemAvailable，不能推断任意并发峰值、无故障长期运行或高可用。扩容、长期观察与灾备有独立证据要求。

演示前准备：使用公网地址而非 127.0.0.1；提前检查登录和角色授权；选一份可公开讲述的手册；准备一条成功工单与一条客服已完成记录作回看材料；不投屏密码、私有配置、真实客户内容或模型密钥。现场若出现失败，说明事实并回看已有证据，不清理失败记录。
