## 1. 当前结论

下一阶段是第五阶段。第四阶段已完成约定的应用 Studio、任务工作台和共享能力本机闭环，并有真实 DeepSeek/OpenAI、浏览器、21 表恢复及 Linux/Windows CI 证据。它不等于生产容量、可用性、灾备目标和长期运行保障已经验收。

第五阶段在现有执行底座上补充治理与验收；第六阶段仍负责 OpsAgent 和正式客服业务的生产迁移、流量切换、旧执行职责退出。PDF/向量知识、长期记忆、任意代码沙箱、并行子 Agent 等功能扩展不自动并入第五阶段；若实际业务必须依赖它们，应另列产品能力工作包。

## 4. 推荐架构选择

继续采用 Java + MySQL，复用现有 API/worker 开关与 SQL 账本。先以一个 API/BFF 和两个 worker 验证工程能力，Linux 预发布使用真实独立进程；跨主机故障结论必须在独立主机上验证。同一宿主机的多容器不证明宿主机高可用。

控制台首版建议接受服务重启后重新登录，采用单活 BFF 与可恢复入口；优先把执行可靠性与恢复流程验收清楚。若目标要求入口无中断、BFF 主动多活或会话跨实例连续，则升级共享会话设计并增加基础设施/凭据加密与轮换验收，不能只加负载均衡。此项由可用性要求推导，不要求用户先选择 Redis 等技术产品。

监控推荐采用标准指标接口、Prometheus/Grafana 与告警接收组件，已有监控环境优先复用；日志/trace 用关联 ID 串联，持久 Run 事件继续作为审计依据。指标默认不使用 Run ID、原问题文本等高基数字段。测试通知用独立接收端，不擅自向真实群发送消息。

本阶段无吞吐证据要求引入 Kubernetes、消息队列或额外执行引擎。若压测证明 SQL 调度不达标，再针对瓶颈调整；不通过删除审批、防重或授权检查换取性能。

## 5. 已确认的验收目标（不是已测能力）

| 项目 | 建议初始目标 | 测量口径 |
|---|---|---|
| 试点规模 | 至少 2 个业务/项目，10 个并发执行任务，模型并发上限 5 | 执行并发与人工等待中的活跃任务分开计数；限额可调；使用已验证研究/知识助手及独立客服试点 |
| API 压测 | 持续 10 请求/秒；短时 2 倍突发 | 固定读写比例、结果大小和历史数据量；受控依赖下测试机制，真实模型验证另外记录，不无限增加外部调用 |
| 平台响应 | 非模型同步 API 的 P95 ≤ 500ms；未饱和时队列 P95 ≤ 2s | 包含真实授权检查；模型生成、人工等待分别统计；饱和时按明确排队/拒绝策略验收 |
| 可用性 | 初期内部试点月度 99.5% 目标 | 总体入口与依赖分项都记录，不能把供应商故障从用户体验里隐去；生产月度目标需完整观察周期，7 天试运行不能证明月度达标 |
| 恢复 | RPO ≤ 15 分钟，RTO ≤ 60 分钟 | RPO 是灾难可丢数据窗口，RTO 从发现/宣布故障到安全恢复约定服务；含恢复核验和外部效果处置。未决写无法确认时必须隔离，不能为达时间指标盲目重放 |
| 观察 | 本机至少 24 小时持续负载；预发布至少 7 天含故障/升级/恢复演练 | 自动化实施期间的持续测试，正式观察任务需单独安排；真实业务写操作不在默认范围 |
| 数据保留 | 任务输入/输出及导出 30 天，诊断 trace 14 天，审计元数据 180 天，备份 30 天 | 只处理满足条件的终态数据；在用知识/发布及活跃任务不按30天删除；先 dry-run。未决审批/UNKNOWN 与关键幂等防重摘要按安全依赖继续保留 |

历史数据规模至少覆盖 10 万终态 Run 加持续活跃/等待任务；若首轮测得硬件不足，先报告瓶颈和容量结果，再调整资源或经用户认可修改目标，不放宽断言隐藏问题。

金额展示区分供应商确认用量、估算价格和 UNKNOWN 预留；测试费用沿用既有“必要验证不限额”的授权。正式运行的月度预算、单项目额度、超额后排队/拒绝规则需在生产启用前确定，测试不限额不自动扩展为生产不限额。

平台限额约束本地准入、派发与账本，不能把本地超时或取消当成远端服务已经停止。远端实际并发、迟到计费和未确认用量需保守占用/告警与独立核验，不宣传绝对账单硬上限。第一版建议正式额度达到后拒绝新任务，已接收任务按原预留与安全停机语义处理；此规则属于生产预算确认内容。

## 6. 三组选择的确认记录

1. **实施环境与第五阶段终点。** 推荐先本机完成工程/故障测试，再用独立 Linux 预发布环境完成部署和7天观察。需确认是否纳入本轮，以及是否已有可用服务器/数据库/备份目标；没有预发布资源也能推进工程，但只能交付“第五阶段工程完成、生产验收待完成”。公网开放、生产切流仍是另外的动作。
2. **验收规模与服务目标。** 是否按第5节候选参数作为第一版目标。若需几十/上百任务并发、99.9%以上可用性、近零数据丢失，应在实现前提出；这些要求会改变主机数量、数据库方案、会话设计与成本。硬件和配额未知时不承诺达标。
3. **数据与运营策略。** 是否接受候选保留期限、RPO/RTO与人工处置原则。告警渠道/接收人、备份存放位置、实际保留约束和正式预算最晚在预发布/生产启用前提供。可先实现可配置策略和模拟告警，未确认前不执行真实历史清理、不发送真实群通知。

无需重新确认的既定事项：中台控制台继续放当前仓库；接现有身份；DeepSeek优先并保留OpenAI通用适配；必要测试费用沿用授权；开发分支使用 `develop/`；业务正式迁移保留在第六阶段。

以上三组推荐已被用户接受。环境进一步明确为本轮只做本机工程与部署包；其余数值沿用。告警真实接收人、外部备份目标和生产金额预算仍没有具体值，本轮通过隔离测试接收端和可配置策略验收，不虚构这些生产配置。

## 7. 第五阶段完成判定

“代码写完”“本机测试通过”“预发布验收通过”分别记账。只有约定负载、故障、恢复、升级、权限、告警、运行手册和观察期全部通过，才在约定部署范围内称为完成第五阶段。可用性目标超出单机恢复能力时必须升级部署方案，不能用单机试点结果声称多机高可用。

本轮已获准实施。使用独立本机验收数据库与合成数据完成工程和故障验证，保留第四阶段实例与记录；部署包准备就绪后交付。正式业务切流仍属于第六阶段。

## 8. 后续专项：ACP（本轮不实现）

用户明确 ACP 指 **Agent Communication Protocol（Agent 之间通信）**，不是 Agent Client Protocol。该专项在第五阶段之后单独推进，与第六阶段业务接入协调安排。

后续先核实目标协议的维护状态、版本和目标系统，评估与现有 Agent 通信协议生态的兼容选择，再设计 Agent 能力发现、身份委托、任务提交/查询/事件、取消、人工请求和产物的适配。远端任务 ID 与本平台 Run/调用账本保持明确关联；断连、幂等、权限撤销、预算归属和结果未知需要专项验收。不能通过引入协议绕过现有审批或复制执行状态机。

交付顺序拟为：协议与使用场景核对 → 适配层设计 → 两个独立 Agent 的互操作试点 → 故障/权限/版本兼容验收。本轮不增加 ACP endpoint、依赖、后台服务或协议兼容承诺。
